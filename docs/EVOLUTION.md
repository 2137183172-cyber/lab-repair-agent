## 案例一：为什么“注册成功”还可能无法接单

原修复记录指出，账号表存在工程师身份，并不保证工程师业务档案已创建。用户可能完成登录，却在接单入口遇到“工程师不存在”。

修订逻辑是让注册/身份升级与业务档案同步，并考虑历史记录补齐。这提醒后续 Agent 工具设计：**身份声明、可用业务对象与动作权限是不同条件**。

实现入口：[用户与工程师建档](../backend/routes/user.js)、[工程师业务接口](../backend/routes/engineer.js)。

## 案例二：为什么支付状态必须影响工单状态

原修复记录指出，报价审批可能直接进入维修，付款后又只更新支付标记，导致用户、工程师与平台看到的阶段不同。

修订后的主线是报价/接单、付款、维修、待验收、确认完成。实际分支受角色与报价方式影响，不能把流程图当成所有状态的完整规格。

```mermaid
flowchart LR
    A[报修] --> B[接单 / 报价]
    B --> C[付款确认]
    C --> D[维修]
    D --> E[待验收]
    E --> F[确认完成]
```

实现入口：[工单](../backend/routes/order.js)、[报价](../backend/routes/quote.js)、[支付](../backend/routes/payment.js)。公开版未完成真实支付联调。

## 案例三：为什么需要协调方的独立工作流

工程进度和平台处理进度不是同一件事。报价审核、指派责任和平台复核需要独立记录。当前代码因此包含协调方路由与平台状态。

代价是两个状态维度的一致性更难维护，需要统一转换规则和接口级测试，而不是继续在各页面堆条件。

实现入口：[协调方流程](../backend/routes/broker.js)、[工单模型](../backend/models/RepairOrder.js)、[日志可见性](../backend/config/logVisibility.js)。
