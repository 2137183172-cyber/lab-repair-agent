# 从工作流到 Agent 工具层

## 决策：先建立确定性业务规则

故障描述可以由模型辅助整理，但报价确认、开修与验收会改变真实业务状态。现有项目先表达角色与流程，为后续工具调用提供基础。局限是目前规则分布于多个路由，尚不能宣称具备统一、完备的执行控制层。

## 决策：区分维修进度与平台处理进度

一个状态字段难以同时说明工程师在做什么、平台审核到哪一步。当前模型表达两个维度，使责任更清楚；代价是需要检查跨维度的一致性。

## 计划中的工具契约

每个工具需要描述：输入、调用角色、工单前置状态、允许修改的字段、幂等键、失败语义与人工确认点。只读匹配与实际选标/付款等动作分开。

## 待完成的合成测试矩阵

| 测试 | 应证明什么 |
|---|---|
| 相同操作重复调用 | 不重复创建支付/报价或推进状态 |
| 过期状态请求 | 明确拒绝或要求重新读取，不覆盖新状态 |
| 角色不匹配 | 不因模型要求或前端隐藏按钮而放行 |
| 工具链跳步 | 不绕过付款、验收等必要阶段 |
| 并发选标 | 不产生两个互相冲突的最终选择 |
| 外部服务失败 | 状态与对外说明保持一致，可识别待人工处理事项 |

以上是未来验收标准，尚无完整测试结果。当前公开验证范围见 [VALIDATION.md](VALIDATION.md)。
